# Link agent skills by default, and prune only what the repo can prove it installed

The repo ships skills and rules for two agents. Claude Code reads `~/.claude/skills/` and `~/.claude/rules/`. pi reads `~/.agents/skills/`. Neither agent reads the other's directory. Both directories also hold entries the user installed from elsewhere: on the machine this ADR was written for, `~/.agents/skills/` held 20 skill directories, and 4 of them came from this repo. The previous `install_pi_skills` ran `rm -rf ~/.agents/skills` and then `cp -r`. That deleted the other 16 on every deploy, and left the user's hand-made `~/.claude/skills` links dangling.

The decision, in three parts:

*The installer links entries into this checkout by default, and offers a copy as the alternative.* Each module asks once, with `choose -d 1` and link first, so `-y` and a bare Enter both link. A link makes the checkout the single source of truth. A change to a skill in the repo is a change to the installed skill, and `git pull` updates every agent at once.

*A destination entry is ours only when it is a symlink whose target resolves inside one of the source directories that feed that destination* (see [[Owned entry]] in CONTEXT.md). The prune removes owned entries the repo no longer ships, and nothing else. Copy mode cannot prune, because a copy carries no proof of origin. The installer's comments state that limit rather than hide it behind a workaround.

The scope of the test — the sources that feed the destination, not `$DOTFILES` as a whole — is what keeps the rule honest. This ADR says `claude/skills/` deliberately never reaches pi. A user who wants `rate-limit-status` there anyway links `~/.agents/skills/rate-limit-status` at it by hand. Under a `$DOTFILES`-wide test that link is "ours", and the next `install_pi_skills` deletes it. The rule would break the invariant in the same breath as it states it. Under the scoped test, pi owns only what came from `pi/skills/`, and the user's link survives.

*`~/.claude/skills/` has exactly one owner, the claude module,* which installs `claude/skills/` and `pi/skills/` into it. The pi module writes only to `~/.agents/skills/`. The two modules share in one direction only: `claude/skills/` never reaches pi, because a skill like `rate-limit-status` reads Claude Code's own OAuth token and means nothing there.

Why this direction and not others:

- *Keep a manifest of installed paths and prune from that.* Works in copy mode too, which ownership-by-symlink does not. Rejected because the manifest is state that can lie. Delete it by hand, and the installer forgets what it owns. Restore an old one, and it prunes something it never installed. The symlink target is the proof, and it cannot drift from the thing it describes.
- *Let both modules write into `~/.claude/skills/`, each with its own prune.* On every deploy, the claude module would prune pi's links as "not shipped by claude", and pi would prune claude's — a mutual delete loop. A fix needs per-module ownership markers, which is the manifest above.
- *Point `~/.claude/skills/<name>` at `~/.agents/skills/<name>` rather than at the checkout,* the way the user had built it by hand. Rejected: Claude's view of a skill would then depend on an earlier run of the pi module. In copy mode it also makes the installed skill a copy of a copy.
- *Have pi read `~/.claude/skills` directly via its `skills` setting,* which pi supports. It would remove the cross-install entirely, but it leaks Claude-specific skills into pi, and it puts this repo in charge of merging `~/.pi/agent/settings.json`.
- *Back displaced entries up in place, as `backup_file` does for files.* Both harnesses discover skills recursively, so `~/.claude/skills/rate-limit-status.bkp/SKILL.md` would appear as a skill named `rate-limit-status.bkp`. Backups go to a sibling of the destination root instead — `~/.claude/skills.bkp/` — which neither harness scans.
- *Ask about collisions per entry.* Rejected as the default. The installer asks once for every destination a module owns, after it names what collides. A per-entry prompt is still available as the third answer. One scan, one question, and the whole picture is visible before the answer.
- *In copy mode, overwrite a destination that differs and merely name it,* the way `report_settings_drift` names overwritten settings keys. That reads well for a settings file the repo wrote, but a destination directory is not one. An edited copy of ours and a skill that was there first are byte-for-byte the same, so "name it and overwrite" would silently delete the second. A copy whose bytes match the source counts as ours and passes quietly. Anything else is a collision, and goes through the same question link mode asks. A re-run stays silent, and nothing is destroyed without an answer.

The installer enforces two preconditions rather than accommodates them, in the spirit of ADR-003's anchor. First, a name shipped by both `claude/skills/` and `pi/skills/` stops the deploy. The installer scans for collisions before it installs anything, so the second install would otherwise back up the link the first just made, on every deploy forever. Second, a choice of copy mode on a host without `diff` stops the deploy too. Without `diff` every copy looks edited, and the default policy would file the same backup again on every run.

The load-bearing property is that the installer never removes a path it cannot prove it created. Every destructive branch — prune and collision — needs either that proof or an explicit answer from the user.
