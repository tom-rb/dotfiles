# Pin pi packages, and install them one spec at a time

The repo wants pi to come up on a new machine with a known set of extensions. pi already has a declarative place for that list: the `packages` array in `~/.pi/agent/settings.json`. The repo owns that array through the same template merge the claude module uses, so the list lives in `pi/settings.json` and the merge replaces whatever the machine held.

That settles where the list lives. What it does not settle is how the packages get onto the disk, and the two candidate commands do not behave the way their names suggest.

*Every spec the repo ships pins a version, and `install_pi_packages` calls `pi install` once per spec.* `pi update --extensions` reads the same array and installs what is missing, in one call, which looks like the obvious reconcile command. It is not, for pinned specs: it skips them. Measured against pi 0.79.1 with a clean agent directory and a template holding `npm:pi-simplify@0.2.3` and `npm:pi-fabric`, the command installed `pi-fabric`, never touched `pi-simplify`, printed no warning, and exited 0. The documented behaviour is that pinned specs are skipped by package updates. The consequence, undocumented, is that a pinned spec is never installed by that command at all. A deploy that trusted it would leave a fresh machine silently missing every pinned package.

So the choice is between pinning and one call per spec, or floating versions and one call for the whole list. This repo pins pi itself (`PI_VERSION`, "bump deliberately") and installs asdf from a pinned tarball, and the same reasoning applies here: a deploy that resolves `latest` gives two machines built a week apart two different sets of extensions, and gives no way to say which version a report came from.

The costs are real and accepted. Nothing will announce that a pinned package has moved on, because the command that would notice is the one pinning takes off the table; bumping is a hand edit to `pi/settings.json`. And the step spends about 1.5 seconds per spec on a deploy with nothing to do.

*`pi install` decides whether there is work to do, not the repo.* Re-running it on a spec already installed at that version short-circuits before it reaches npm, at the 1.5 seconds measured above. The alternative is for the step to read `~/.pi/agent/npm/node_modules/<name>/package.json`, compare its version against the spec, and skip the call. That is pi's own freshness check, re-implemented in shell against a directory layout pi is free to change, to save a second per package. It is the kind of duplicated invariant that rots quietly. Revisit if the list grows past roughly ten specs.

*The step attempts every spec and reports the failures afterwards.* Stopping at the first failure hides which of the remaining specs would also have failed, and a network flake on one package is no reason to leave the rest uninstalled. Warning and returning 0 is worse: a half-installed set that reports success is the outcome that gets discovered three deploys later. So the loop runs to the end, names each failure as it happens, and the step returns non-zero. This is also how `pi update --extensions` behaves.

*A missing `pi` at this point stops the module.* `install_pi_program` runs earlier in the same wizard and either put pi on PATH or already stopped the run, so a missing binary here is a PATH bug, not a state the machine can legitimately be in. The claude module's `report_claude_install` warns and carries on instead, but that is a different situation: claude's settings are worth writing before Claude Code exists, whereas there is nothing to install packages into without pi.

Why not the alternatives:

- *A pi package of our own that lists the others as `bundledDependencies` and re-exports their extensions.* pi supports this, and it would reduce the list to one spec. Rejected: pi does not run `npm install` for a local-path package, verified against 0.79.1, so the repo would have to run npm itself and keep a `package.json` in sync with the array it already maintains. `pi install` on an absolute path also rewrites it into settings as a path relative to `~/.pi/agent`. More moving parts, same outcome.
- *Let `pi install` own the list and drop `packages` from the template.* `pi install` writes the spec into settings itself, so the array would be machine state and the template would not need to name it. Rejected: nothing would then remove a spec the repo stopped shipping. Template ownership of the array is what makes removal work.
- *Float the versions and call `pi update --extensions` once.* One call, no per-spec cost, and updates arrive on their own. Rejected for the determinism reason above. It remains the right answer if this repo ever decides it would rather track upstream than pin.
- *Prune the npm tree when a spec leaves the template.* `pi remove` exists, and pruning would mirror how the repo treats [[Owned entry]] directories. Rejected for now: the dead code loads nothing once the array no longer names it, and the disk cost is bounded. The removal is still announced, because the array is a key the template overwrites and `report_settings_drift` names it like any other.

The load-bearing property is that `pi/settings.json` is the whole truth about which packages the repo wants, and that a clean machine and a deployed one end up with the same versions of them.
